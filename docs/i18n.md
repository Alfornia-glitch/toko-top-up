# Internationalisation (i18n)

The app is Indonesian first (`id`, base locale) with English (`en`) behind a language toggle.
It uses [Paraglide JS](https://paraglidejs.com) (inlang): every message compiles to a typed
function, `m.some_key({ param })`.

## How the locale is chosen

- Strategy is `cookie` then `baseLocale` (`project.inlang/paraglide.config.ts`). No URL prefixes, no
  Accept-Language sniffing: everyone sees Indonesian until they press ID / EN.
- The `LanguageSwitcher` component (storefront `SiteHeader`, `AdminHeader`) calls `switchLocale()`,
  which writes the `PARAGLIDE_LOCALE` cookie and reloads the page.
- Pages are SPA shells (`ssr = false`) and the prerendered ones (`/`, `/categories`, `/products`,
  `/help/*`, `/privacy-policy`) are built in Indonesian. The client reads the cookie on every
  `m.*` call and `src/routes/+layout.svelte` syncs `<html lang>`.
- `src/hooks.server.ts` runs `paraglideMiddleware` first, so server code (`m.*` in endpoints, zod
  messages) sees the request locale; `app.html` holds `%paraglide.lang%`.
- Generated code lives in `src/lib/paraglide/` (git-ignored). It is rebuilt by the Vite plugin
  (`dev`, `build`, `vitest`), by `pnpm run i18n:compile`, by `pnpm run check`, and on `pnpm install`.
  The inlang message-format plugin is loaded from jsdelivr, so the first compile needs network.

## Message files and ownership

One JSON file per area and locale, merged by the plugin's array `pathPattern`
(`project.inlang/settings.json`). Two files for each area: `messages/<area>/id.json` and
`messages/<area>/en.json`. **Edit only your own area's files** so parallel work never conflicts.

| Area         | Files                        | Key prefix                         | Owns                                                       |
| ------------ | ---------------------------- | ---------------------------------- | ---------------------------------------------------------- |
| `common`     | `messages/common/*.json`     | `common_`                          | Shared vocabulary (Save, Cancel, Orders, ...), units, ages |
| `labels`     | `messages/labels/*.json`     | `labels_<kind>_<value>`            | Enum labels (statuses, roles, audit actions)               |
| `account`    | `messages/account/*.json`    | `account_` / `cart_` / `checkout_` | `routes/account`, `cart`, `checkout`                       |
| `admin`      | `messages/admin/*.json`      | `admin_`                           | `routes/(admin)` and admin-only components                 |
| `storefront` | `messages/storefront/*.json` | `storefront_` / `auth_`            | Storefront and auth routes, `frontend/pages`, `content/`   |
| `components` | `messages/components/*.json` | `components_`                      | Shared feature components and `frontend/modules`           |
| `ui`         | `messages/ui/*.json`         | `ui_`                              | shadcn primitives in `components/ui`                       |
| `errors`     | `messages/errors/*.json`     | `errors_`                          | Translations of server error codes                         |

Rules:

- Keys are `snake_case` and start with the area prefix, then page/component, then the purpose:
  `account_orders_empty_title`, `components_site_header_cart`. Keys are global across areas, so
  never reuse a prefix owned by another area. Reach for `common_*` before adding a duplicate.
- Always add a key to **both** `id.json` and `en.json` (keep each file's keys in the same order).
  Keep the `"$schema"` line at the top.
- Brand names ("Top Up Store", "Shopix") are never translated.

## Using messages

```svelte
<script lang="ts">
	import { m } from '#lib/paraglide/messages.js';
</script>

<h1>{m.account_orders_title()}</h1><p>{m.account_orders_found({ count: orders.length })}</p>
```

Params use `{name}` in the text: `"account_orders_found": "{count} pesanan ditemukan"`. Pass them as
an object. Messages are plain functions, so they are reactive only through the page reload the
language toggle performs; do not cache their result in module scope, call them in the template, in
`$derived`, or inside functions.

Plurals: Indonesian has no plural forms, so write one string with the count (`"{count} item"`).
English may use paraglide variants; see `common_items_count` in `messages/common/en.json`
(`declarations` / `selectors` / `match` with `plural`) or phrase it without a plural (`Items: {count}`).

Attributes and placeholders go through messages too (`placeholder={m.common_search_placeholder()}`,
`aria-label`, `title`, toast text, `<title>` / SEO strings).

## Formatting

Never hard-code `'en-US'`. Use `src/lib/frontend/modules/commerce/format.ts`, which follows the
current locale (`intlLocale()` from `#lib/frontend/i18n/locale.ts`: `id-ID` / `en-US`):

- `formatMoney(amount, currency?)` whole IDR rupiah.
- `formatDate`, `formatDateTime`, `formatNumber`, `formatPercent`, `formatBytes`,
  `formatDuration(ms)`, `formatAge(date)` (translated units; keys are `common_unit_*`,
  `common_duration_*`, `common_age_*`).
- For other `Intl` use: `new Intl.NumberFormat(intlLocale(), ...)`.

## Enum labels

Raw API values (statuses, roles, audit actions) must not be shown as is. Use
`#lib/frontend/i18n/labels.ts`:

```ts
statusLabel('order', order.status); // kinds: order payment fulfillment return ticket priority
// gift_card gift_card_tx coupon coupon_type newsletter product review cart return_type
// return_resolution payment_type reject_reason role audit_action danger_action misc
roleLabel(user.role);
auditActionLabel(log.action); // 'user.set_role' -> labels_audit_action_user_set_role
anyStatusLabel(value); // when the kind is unknown
```

`<StatusBadge status kind?>` (admin) and `<OrderStatusBadge>` already use them. A new enum value
needs `labels_<kind>_<value>` in both `messages/labels/*.json` (dots become underscores); unknown
values fall back to a humanised string. `content/status.ts` keeps the legacy `*_STATUS_LABELS`
maps for old call sites; prefer `statusLabel(kind, value)` in new code.

## Errors

API errors are `{ error, code, params? }`. `error` is the English server message (still there for
old consumers), `code` is a specific `messageKey` when the throw site gives one, otherwise the
coarse `ErrorCode` (`NOT_FOUND`, `CONFLICT`, ...).

Server: `throw new ConflictError('Your cart is empty', { messageKey: 'cart_empty', params: {} })`;
build responses with `errorBody(error)` from `#shared`.

Client: `apiFetch` / `api.*` throw `ApiError` (carries `code` and `params`). Show it with

```ts
import { errorMessage } from '#lib/frontend/i18n/index.ts';
toast.error(errorMessage(error, 'account_orders_load_failed'));
```

Lookup order: `errors_<code lowercased>` (so `cart_empty` -> `errors_cart_empty`, `CONFLICT` ->
`errors_conflict`), then the server message, then the fallback key, then `errors_request_failed`.
Add new codes to `messages/errors/{id,en}.json`.

Zod validation messages (`details` in responses) are translated on the server per request
(`src/lib/server/http/zod-locale.ts`, called from the paraglide handle).

## Keep literal

- The `DELETE` confirmation keyword on the admin danger page: the server compares it. Translate the
  sentence around it, not the word.
- Enum values, API field names, route paths, cookie names, CSS class names, `data-name` attributes
  (used by `layout.css`), and brand names.
- Currency codes and number placeholders inside messages (`IDR`, `{count}`).

## Checklist for a new string

1. Pick the key in your area (`<area>_<place>_<purpose>`), add it to `id.json` and `en.json`.
2. Use `m.<key>()` in the code (the generated types fail `pnpm run check` for a missing key).
3. Dates, numbers, sizes: use the formatters. Enum values: use the label helpers.
4. `pnpm run check`, `pnpm run lint`, and flip the toggle to EN once to see the result.
